# Мои пары 72

Сайт: https://moi-pary72.github.io/moi-pary/

Официальный источник: [страница техникума](https://mck72.ru/learners/information-on-learning-process/training-schedules/),
[публичный Яндекс Диск](https://disk.yandex.ru/d/Xc08g8WbTavdHQ).
Сайт показывает текущую и следующую недели в часовом поясе Тюмени (UTC+5).

## Проверки и обновление

```sh
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python scripts/sync.py
# Полная повторная загрузка независимо от метаданных:
python scripts/sync.py --force-download
python -m http.server 8000
```

Workflow `sync.yml` запланирован на 17-ю и 47-ю минуты каждого часа UTC.
Это целевая частота примерно раз в 30 минут, а не гарантия GitHub Actions.
Ручной запуск: Actions → Refresh timetables from Yandex Disk → Run workflow.
Кнопка на сайте проверяет опубликованную копию, не запускает Actions.

При неизменённых modified/size/md5 используется ранее проверенная версия
того же парсера и недели. Не реже чем через 24 часа с последнего скачивания
файл загружается заново. Проверяются размер, MD5 (когда предоставлены),
формат XLS, шесть дат недели, группы, занятия и время. При потере групп или
более 40% занятий сохраняется прежняя версия и требуется проверка источника.
Новая версия структуры не принимается молча. Непубликация следующей недели
считается ожидаемой только пока папка отсутствует и нет предыдущих данных.

`schedules.json`: `last_changed_at` — последнее изменение содержимого
расписания, `generated_at` — формирование JSON. `sync-status.json`:
`last_attempt_at` — попытка; `last_successful_checks[неделя][отделение]` —
успешная проверка метаданных/скачивание; `checks` — результат последней попытки.
`downloaded_at` и SHA-256 в данных отделения фиксируют проверку самого XLS.
Ошибка не обновляет время успешной проверки и не затирает рабочую неделю.

Обновляющий процесс сначала сохраняет рабочие данные и честный статус,
затем возвращает ненулевой код при ошибке источника. Workflow публикует
сохранённые данные и статус, запрашивает сборку существующего GitHub Pages,
после чего отмечает ошибку задания. Права: contents:write, pages:write.
Публикация выполняется из main; отдельная тестовая ветка сайт не заменяет.
Браузер получает JSON с cache:no-store и уникальным параметром URL.

Неизвестный кабинет хранится как пустая строка и показывается «Не указан».
Реальные обозначения (`112А/1`, `АЗ/1`, `БКИ`, `ДО`) сохраняются.
Парсер xlrd читает сохранённые результаты формул, не вычисляет формулы.
Ошибки Excel отклоняют файл. Объединённые пустые ячейки не заполняются
выдуманными занятиями или кабинетами; повторяющиеся точные строки удаляются.

## Смена недель и задержки планировщика

Excel из корня сначала проверяется по реальным шести датам, а затем относится
к соответствующей неделе. Именованная папка не отменяет проверку дат XLS.
Если корень и папка содержат одну неделю, выбирается более новая официальная
версия по `modified`; повреждённый файл не заменяется молча успешным статусом.
При отсутствии файлов завершившейся (после субботы) недели статус `archived`,
будущей — `pending`. Отсутствие текущей недели, сбой источника или испорченный
файл остаются ошибкой. Последняя корректная версия сохраняется.

Статусы отделений каждой недели: `confirmed`, `archived`, `pending`,
`unavailable`, `invalid`. Время успешной проверки обновляется только при
подтверждении конкретного отделения конкретной недели. Интерфейс вычисляет
индикатор и подробности заново при переключении вкладки. По истечении прежних
40 минут он сообщает «Расписание есть · ждём проверку», а не объявляет сами
данные неправильными. Время получения копии сайта не выдаётся за проверку Диска.
Кнопка «Обновить копию сайта» не запускает синхронизацию.

Расписание GitHub Actions — best effort. Аудит 15.11.2026 обнаружил интервалы
между автоматическими запусками 3:57:38 и 6:31:33. Workflow активен, запуск
начинался через секунды после создания; следовательно, основной разрыв был
до создания запуска, а не внутри синхронизации или Pages. GitHub Status при
проверке сообщал All Systems Operational; установить внутреннюю причину
каждого пропущенного cron из API репозитория невозможно.

Подготовлен `repository_dispatch` с типом `refresh-timetables`. Он позволяет
впоследствии добавить независимый резервный планировщик. Внешние сервисы
НЕ подключены, секреты им не переданы. Бесплатный практический вариант:
независимый cron → dispatch этого workflow → проверка времени
`last_successful_checks` и уведомление владельцу при задержке. Потребуются
отдельное согласие на сервис и ограниченный этим репозиторием доступ.
Это снижает зависимость от schedule, но GitHub всё равно не даёт SLA.
При наличии постоянно включённого собственного компьютера тот же Python
может запускаться системным cron независимо от GitHub Actions; питание,
сеть и доступ к репозиторию тогда обеспечиваются владельцем.

Регрессионная проверка JavaScript входит в unittest и требует Node.js 22
(настроен в Actions). Для проверки опубликованного интерфейса:
`python docs/check_site.py https://moi-pary72.github.io/moi-pary/`.
Подробности аудита: [docs/diagnostics-2026-11-15.md](docs/diagnostics-2026-11-15.md).
